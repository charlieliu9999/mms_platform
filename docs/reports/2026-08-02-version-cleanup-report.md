## 清理规则

### 版本优先级
1. V开头的版本优先于其他版本（如 V3.8.2 > 3.8.1）
2. 同类型版本按版本号降序排列（如 V3.8.2 > V3.8 > V3.7）

### 去重逻辑
```sql
-- 使用窗口函数为每个检查项目分配排名
ROW_NUMBER() OVER (
    PARTITION BY checkitem_code  -- 按检查编码分组
    ORDER BY
        CASE
            WHEN version LIKE 'V%' THEN 1  -- V版本优先
            ELSE 2
        END,
        version DESC  -- 版本号降序
) as rn

-- 只保留排名第1的记录（最新版本）
WHERE rn = 1
```

### 删除策略
- **软删除**: 标记 `is_deleted=1`，不物理删除
- **可恢复**: 如需恢复某个版本，可更新 `is_deleted=0`
- **不影响现有逻辑**: 所有查询都已过滤 `is_deleted=0`

## 后续建议

### 1. 更新版本回退配置
当前 `VERSION_FALLBACK` 仅包含 V3.8/V3.9，建议统一为：

```python
VERSION_FALLBACK: Dict[str, List[str]] = {
    'latest': ['V3.8.2', 'V1.0-imported'],  # 默认使用最新版本
    'V3.8.2': ['V3.8.2'],
    'V1.0-imported': ['V1.0-imported'],
}
```

### 2. 统一版本命名规范
- 建议未来所有导入都使用 V{major}.{minor}.{patch} 格式
- 避免使用特殊标记（如 V1.0-imported），改为 V1.0 或 V4.0

### 3. 定期清理机制
- 建立版本清理策略（如保留最近3个版本）
- 新版本发布时自动标记旧版本为已删除
- 定期执行物理删除释放存储空间

### 4. 版本管理增强
- 在数据库中添加 `is_active` 字段（区分已删除和未激活）
- 添加 `deprecated_at` 字段记录版本弃用时间
